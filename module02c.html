6  Data Manipulation

With a dataset in R and inspected, we can start doing things to it. Most data analysis involves repeating a surprisingly small number of operations: keep certain rows, keep certain columns, create or change a column, sort the rows, calculate summary statistics, and do those calculations separately for different groups.

The tidyverse package dplyr gives us a function for each of these jobs (you will often see them called the dplyr “verbs”). None of the operations are new – each is the R form of something from the Excel modules:

Question dplyr function Excel counterpart
Which rows do I want? filter() filtering
Which columns do I want? select() keeping certain columns
What new column do I want? mutate() a formula in a new column
In what order do I want the rows? arrange() sorting
What summary do I want? summarise() summary formulas
That summary separately for groups? group_by() a PivotTable

Once you understand these operations, most everyday data manipulation in R is a matter of combining them.

Learning Objectives

By the end of this chapter you should be able to:

  1. Use filter(), select(), mutate(), and arrange() to manipulate a data frame.
  2. Chain several operations together using the pipe, |>.
  3. Use summarise() to calculate statistics from a data frame.
  4. Use group_by() with summarise() to calculate statistics separately for groups.
  5. Read a longer pipeline from top to bottom and explain what each step does.
  6. Save a result to a CSV file.

The Data

We continue with the canola trial data from the last chapter, in the same project folder. Since this chapter does a new job, it gets a new script: code/2_data_manipulation.R. Start it with a header, then load the tidyverse and read the data in:

# ---
# Title: Manipulating the canola trial data
# Author: Your Name
# Date: 2026-10-06
# Description:
#   Filters, transforms, and summarizes the canola trial data
#   using the dplyr functions.
# ---

# Load packages
library(tidyverse)

# Read in the data
trial_data <- read_csv("data/canola_trial.csv")

R displays the fields with yields above 50 bu/ac, but it does not remove the other fields from trial_data – check nrow(trial_data) and all 120 rows are still there. filter() takes trial_data as input and returns a new data frame as output; if we only display that output, R does not save it. Now there are two objects: trial_data, the original 120 fields, and high_yield, the filtered subset. This is a useful feature – you can experiment with transformations without changing the original data. Throughout the chapter, an example without <- is just displaying a result; add a name in front when you want to keep it.

6.1 Data Manipulation Functions

Two of the four basic functions mainly affect the rows: filter() chooses rows, and arrange() changes their order. Two mainly affect the columns: select() chooses columns, and mutate() creates or changes them. Each takes the data frame as its first argument, followed by what to do with it.

6.1.1 filter(): Keep Certain Rows

filter() keeps the rows that satisfy a condition:

filter(trial_data, yield_bu_acre > 50)

Read this as: from trial_data, keep the rows where yield_bu_acre is greater than 50. Text variables work too:

filter(trial_data, variety == "InVigor")

Note the two equals signs: == asks whether two things are equal, so variety == "InVigor" asks “is variety equal to "InVigor"?”. A single = has a different job in R – naming arguments, as in mean(x, na.rm = TRUE) – so writing variety = "InVigor" inside filter() will not do what you want. Also note the quotation marks: "InVigor" with quotes is text; InVigor without quotes would be read as the name of an object, which probably doesn’t exist and would cause an error.

You can combine conditions with & (and – both must be true), | (or – at least one must be true), and ! (not):

filter(trial_data, yield_bu_acre > 50 & variety == "InVigor")
filter(trial_data, fertilizer_kg_ha < 80 | fertilizer_kg_ha > 160)
filter(trial_data, !is.na(rainfall_mm))  # is.na() asks if a value is missing; ! keeps the non-missing

That last one is not hypothetical: three of our fields have no rainfall reading, and this is how you would set them aside.

When you want to match several possible values of the same variable, %in% is easier to read:

filter(trial_data, variety %in% c("InVigor", "DEKALB"))

You do not need to memorize every comparison operator. The idea is that filter() chooses observations by asking a TRUE/FALSE question about each row.

6.1.2 select(): Keep Certain Columns

select() chooses variables rather than observations:

select(trial_data, field_id, variety, yield_bu_acre)
> select(trial_data, field_id, variety, yield_bu_acre)
# A tibble: 120 × 3
   field_id variety    yield_bu_acre
   <chr>    <chr>              <dbl>
 1 C001     InVigor             56.7
 2 C002     DEKALB              62  
 3 C003     Clearfield          53.6
 4 C004     InVigor             51.2
 5 C005     InVigor             49.2
 6 C006     InVigor             51.2
 7 C007     Clearfield          49  
 8 C008     InVigor             56.8
 9 C009     InVigor             61  
10 C010     Clearfield          48.2
# ℹ 110 more rows

The result has the same rows but only those three columns – especially useful with datasets containing dozens or hundreds of variables. You can also drop a column by putting - in front of its name, or keep a range of adjacent columns:

select(trial_data, -rainfall_mm)                 # everything except rainfall
select(trial_data, field_id:rainfall_mm)         # the columns from field_id through rainfall_mm

A relative of select() is rename(), which changes a column’s name without dropping anything: rename(trial_data, yield = yield_bu_acre).

Keep the pair straight: filter() works on rows, select() on columns.

You can create several variables in one call, and later expressions can use variables created earlier in the same mutate():

mutate(trial_data,
       yield_t_ha = yield_bu_acre * 0.0560,
       kg_n_per_bu = fertilizer_kg_ha / yield_bu_acre)

6.2 The Pipe |>

Real questions usually take more than one function. Suppose we want to know: among the InVigor fields, what are the field IDs and yields, ordered from highest to lowest? We know every operation we need – filter to InVigor, select the two columns, arrange by descending yield. Without a pipe, each step’s output becomes the next step’s first argument, and the calls nest:

arrange(select(filter(trial_data, variety == "InVigor"), field_id, yield_bu_acre),
        desc(yield_bu_acre))

That works, but you have to start reading in the middle and work outward. The pipe, |>, lets us write the analysis in the order we think about it. The pipe takes whatever is on its left and feeds it as the first argument to the function on its right, so trial_data |> filter(variety == "InVigor") is exactly filter(trial_data, variety == "InVigor"). Read |> as the word “then”:

trial_data |>
  filter(variety == "InVigor") |>
  select(field_id, yield_bu_acre) |>
  arrange(desc(yield_bu_acre))
> trial_data |>
+   filter(variety == "InVigor") |>
+   select(field_id, yield_bu_acre) |>
+   arrange(desc(yield_bu_acre))
# A tibble: 42 × 2
   field_id yield_bu_acre
   <chr>            <dbl>
 1 C112              70.4
 2 C045              62.8
 3 C033              62.5
 4 C009              61  
 5 C120              60.1
 6 C119              60  
 7 C011              59.5
 8 C052              59.5
 9 C076              59.2
10 C059              58.4
# ℹ 32 more rows

Take trial_data, then keep the InVigor fields, then keep two columns, then sort. Once we use the pipe, we no longer repeat the data-frame name in every function, and a multi-step analysis reads top to bottom. From here on the examples use the pipe. (Older code uses %>% for the same idea; |> is the modern built-in version.)

To keep a result, assign the whole pipeline to an object:

invigor_yields <- trial_data |>
  filter(variety == "InVigor") |>
  select(field_id, yield_bu_acre) |>
  arrange(desc(yield_bu_acre))

Debugging a pipeline

Pipelines also give you a way to debug. When a pipeline produces a result that looks wrong, do not stare at the whole thing and guess. Run it one step at a time: run the first step alone, check the result, add the second step, check again, and keep going. The first point where the data stops looking the way you expect is where the problem is. This works because every step does one thing – and the same habit is how you check a pipeline an AI assistant wrote for you.

6.3 summarise() and group_by()

The four functions so far rearrange or add information while keeping observations as rows. Sometimes we want to collapse the observations into summary statistics. That is the job of summarise().

6.3.1 summarise(): Many Rows Become One

trial_data |>
  summarise(
    mean_yield = mean(yield_bu_acre, na.rm = TRUE),
    sd_yield = sd(yield_bu_acre, na.rm = TRUE),
    n_fields = n()
  )
> trial_data |>
+   summarise(
+     mean_yield = mean(yield_bu_acre, na.rm = TRUE),
+     sd_yield = sd(yield_bu_acre, na.rm = TRUE),
+     n_fields = n()
+   )
# A tibble: 1 × 3
  mean_yield sd_yield n_fields
       <dbl>    <dbl>    <int>
1       53.4     5.77      120

The names on the left (mean_yield, sd_yield, n_fields) become column names in the result; the expressions on the right calculate the values. n() counts the rows.

The contrast with mutate() matters. mutate() keeps the observations and adds information; summarise() collapses the observations into summaries. So trial_data |> mutate(mean_yield = mean(yield_bu_acre)) still has 120 rows, with the overall mean repeated on every row, while the summarise() version returns one row.

6.3.2 group_by(): Calculate Separately for Groups

The overall mean may not be what we want. Suppose we want the mean yield for each variety. group_by() doesn’t change the data – it tells subsequent operations to apply per group:

trial_data |>
  group_by(variety) |>
  summarise(
    mean_yield = mean(yield_bu_acre, na.rm = TRUE),
    sd_yield = sd(yield_bu_acre, na.rm = TRUE),
    n_fields = n()
  )
> trial_data |>
+   group_by(variety) |>
+   summarise(
+     mean_yield = mean(yield_bu_acre, na.rm = TRUE),
+     sd_yield = sd(yield_bu_acre, na.rm = TRUE),
+     n_fields = n()
+   )
# A tibble: 3 × 4
  variety    mean_yield sd_yield n_fields
  <chr>           <dbl>    <dbl>    <int>
1 Clearfield       53.5     5.55       39
2 DEKALB           52.2     6.03       39
3 InVigor          54.5     5.63       42

Take trial_data, then divide the observations by variety, then calculate the statistics separately for each variety. The result has one row per variety. This is the R equivalent of a PivotTable.

Grouping is state that can affect later operations. After a grouped summarise(), ask for an ordinary, ungrouped data frame back with .groups = "drop" when you plan to keep manipulating the result – the capstone example below does this. (There is also an ungroup() function, which appears later in this chapter in a situation where it genuinely matters.)

The central pattern – data |> group_by(group_variable) |> summarise(...) – appears throughout the rest of the book.

6.4 Unit Conversion: A Worked Example

Canadian ag data often comes in mixed units. Canola yields are traditionally reported in bushels per acre (bu/ac) in Canada, but metric tonnes per hectare (t/ha) in global datasets. The conversion for canola is approximately:

\[ \text{yield (t/ha)} = \text{yield (bu/ac)} \times 0.0560 \]

This factor comes from two facts: a bushel of canola weighs about 22.68 kg (canola’s standard 50-lb bushel), and an acre is about 0.4047 ha. So one bu/ac is \(22.68 \div 0.4047 \div 1000 \approx 0.0560\) t/ha. (The exact factor depends on the crop’s bushel weight – a wheat or corn bushel is 60 or 56 lb and gives a different number – so in a real analysis you would look up the right bushel weight for your crop and cite your source.)

The transformation is exactly what mutate() is for:

trial_converted <- trial_data |>
  mutate(yield_t_ha = yield_bu_acre * 0.0560)

trial_converted |>
  select(field_id, yield_bu_acre, yield_t_ha)
> trial_converted <- trial_data |>
+   mutate(yield_t_ha = yield_bu_acre * 0.0560)
> 
> trial_converted |>
+   select(field_id, yield_bu_acre, yield_t_ha)
# A tibble: 120 × 3
   field_id yield_bu_acre yield_t_ha
   <chr>            <dbl>      <dbl>
 1 C001              56.7       3.18
 2 C002              62         3.47
 3 C003              53.6       3.00
 4 C004              51.2       2.87
 5 C005              49.2       2.76
 6 C006              51.2       2.87
 7 C007              49         2.74
 8 C008              56.8       3.18
 9 C009              61         3.42
10 C010              48.2       2.70

The original yield_bu_acre stays in the data alongside the new yield_t_ha, which makes the transformation easy to check.

An extension: different rules for different rows

Sometimes a new variable depends on a condition. Suppose we want to class each field’s nitrogen rate as low, medium, or high. case_when handles it – read this one to understand it rather than to memorize it:

trial_data |>
  mutate(n_rate = case_when(
    fertilizer_kg_ha < 100 ~ "low",
    fertilizer_kg_ha < 150 ~ "medium",
    TRUE                   ~ "high"
  )) |>
  select(field_id, fertilizer_kg_ha, n_rate)
> trial_data |>
+   mutate(n_rate = case_when(
+     fertilizer_kg_ha < 100 ~ "low",
+     fertilizer_kg_ha < 150 ~ "medium",
+     TRUE                   ~ "high"
+   )) |>
+   select(field_id, fertilizer_kg_ha, n_rate)
# A tibble: 120 × 3
   field_id fertilizer_kg_ha n_rate
   <chr>               <dbl> <chr> 
 1 C001                146.  medium
 2 C002                136.  medium
 3 C003                113.  medium
 4 C004                112.  medium
 5 C005                103.  medium
 6 C006                140.  medium
 7 C007                102   medium
 8 C008                137.  medium
 9 C009                142.  medium
10 C010                 97.9 low   
# ℹ 110 more rows

Each line reads “if this condition is true, use this value”, and the first matching condition wins: a field at 120 kg/ha fails the first test and passes the second, so it is “medium”. The TRUE ~ ... line is the catch-all – anything that matched neither condition is “high”. case_when is the R analogue of nested IFs in Excel, and it comes back when we clean data in Chapter 9. The point for now is that mutate() can create variables using rules, not just arithmetic.

6.5 Writing Output

Results so far have existed only inside R. To save one as a file that can be opened in Excel or sent to someone else, pass the object and a filename to write_csv. With our project layout, results go in output/:

variety_summary <- trial_data |>
  group_by(variety) |>
  summarise(mean_yield = mean(yield_bu_acre, na.rm = TRUE),
            n_fields = n())

write_csv(variety_summary, "output/variety_summary.csv")

read_csv brings data into R; write_csv sends a data frame out to a file. Because the output is created by the script, you can always recreate it by running the script again.

6.6 Combining It All

We now have enough tools to answer a realistic question: for each variety and nitrogen-rate class, what was the mean yield in t/ha, and how many fields were observed? Show the highest-yielding class first within each variety.

variety_n_summary <- trial_data |>
  mutate(yield_t_ha = yield_bu_acre * 0.0560,
         n_rate = case_when(
           fertilizer_kg_ha < 100 ~ "low",
           fertilizer_kg_ha < 150 ~ "medium",
           TRUE                   ~ "high")) |>
  group_by(variety, n_rate) |>
  summarise(mean_yield_t_ha = mean(yield_t_ha, na.rm = TRUE),
            n_fields = n(),
            .groups = "drop") |>
  arrange(variety, desc(mean_yield_t_ha))
variety_n_summary

+          n_rate = case_when(
+            fertilizer_kg_ha < 100 ~ "low",
+            fertilizer_kg_ha < 150 ~ "medium",
+            TRUE                   ~ "high")) |>
+   group_by(variety, n_rate) |>
+   summarise(mean_yield_t_ha = mean(yield_t_ha, na.rm = TRUE),
+             n_fields = n(),
+             .groups = "drop") |>
+   arrange(variety, desc(mean_yield_t_ha))
> variety_n_summary
# A tibble: 9 × 4
  variety    n_rate mean_yield_t_ha n_fields
  <chr>      <chr>            <dbl>    <int>

3 Clearfield low               2.57        5

Do not read it as one giant command; read it one step at a time:

  1. Create the variables the question needs: metric yield, and the nitrogen-rate class.
  2. Group the observations into variety and nitrogen-rate combinations.
  3. Summarise each group down to one row: its mean yield and its number of fields. With two grouping variables, .groups = "drop" tells summarise to hand back an ordinary, ungrouped data frame.
  4. Sort by variety and, within each variety, from highest mean yield to lowest.

Each line does one simple thing, and that is the reason for pipes: a good pipeline makes the logic of an analysis visible. Saving the table is one more line: write_csv(variety_n_summary, "output/variety_n_summary.csv").

A slightly harder example

Which fields yielded above the average for their own variety? This needs one new idea: mutate() can operate within groups.

above_variety_average <- trial_data |>
  group_by(variety) |>
  mutate(variety_mean = mean(yield_bu_acre)) |>
  ungroup() |>
  filter(yield_bu_acre > variety_mean) |>
  select(field_id, variety, yield_bu_acre, variety_mean) |>
  arrange(variety, desc(yield_bu_acre))

+   arrange(variety, desc(yield_bu_acre))

The important step is group_by(variety) followed by mutate(). Because the data is grouped by variety, mean() is calculated separately within each variety – and unlike summarise(), mutate() keeps every field and adds its variety’s mean as a new column on each one. This is also where ungroup() earns its place: we are finished calculating within varieties, so we remove the grouping and the later steps treat the result as an ordinary data frame.

You do not need to produce this second pipeline from memory. You should be able to read it from top to bottom and explain what each step is doing. As analyses become more complicated – and especially once AI helps generate the code – that is the skill that matters: looking at a sequence of operations and deciding whether it actually answers the question you intended to ask.
