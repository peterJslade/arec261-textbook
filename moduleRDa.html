7  Starting a Project

Everything so far has come to you ready to use: a tidy CSV, in the right folder, with sensible column names. Real work does not start there. It starts with a question, an empty folder, and a file somebody emailed you.

This module is about the part of data analysis that happens before any analysis: setting up a project, getting data into it, and finding out whether the data can be trusted. It is unglamorous and it is most of the job.

Learning Objectives

By the end of this chapter you should be able to:

  1. Lay out a project folder that someone else can open and run.
  2. Explain why a script should never contain setwd().
  3. Keep raw data separate from anything you have changed.
  4. Write a README that says where the data came from.

7.1 One Folder Per Project

You met the working directory in Section 5.1: the folder R treats as “here”, and the reason read_csv("yields.csv") sometimes cannot find a file sitting right in front of you. The fix suggested there was to keep each analysis in its own folder and open that folder in Positron. This chapter is about what goes in the folder.

A layout that works for almost everything:

canola-trial/
  data/
    canola_trial.csv          <- exactly as it arrived
  R/
    01_clean.R
    02_analysis.R
  output/
    yield_by_variety.png
    summary_table.csv
  README.md

Four ideas are doing the work here.

The project is self-contained. Everything the analysis needs is inside canola-trial/. You can zip the folder, send it to somebody, and it will run on their machine. If your script reaches out to a file somewhere else on your hard drive, it will not.

Raw data is never edited. data/ holds the file as it arrived, and nothing you do ever writes back to it. If you open the CSV in Excel, fix three cells and save, you have destroyed the only copy of what you were actually given – and no record of what you changed. Cleaning happens in the script, where it leaves a trail.

Outputs are disposable. Anything in output/ can be deleted and regenerated by re-running the scripts. That is the test of whether your analysis is reproducible: delete output/, run the scripts, and see whether everything comes back.

Scripts are numbered in the order they run. 01_clean.R then 02_analysis.R. Six months later this tells you where to start, and it forces you to notice when a project has grown a script that has to run third but is named as though it runs first.

7.2 Paths, and Why setwd() Is a Trap

A path is how you tell R where a file is. There are two kinds and the difference matters more than it looks.

An absolute path starts at the root of your hard drive:

read_csv("/Users/peter/Documents/canola-trial/data/canola_trial.csv")

A relative path starts wherever R currently is:

read_csv("data/canola_trial.csv")

The relative version works on any machine where the project folder is open. The absolute one works only on mine. It names a user, a folder layout and an operating system, none of which your classmate or your future self on a new laptop will share.

The same objection applies, more strongly, to putting setwd() in a script:

setwd("/Users/peter/Documents/canola-trial")     # do not do this

This is the single most common reason a script that “works fine” fails for everyone else. It hard-codes one machine into a file you are going to share. Open the project folder instead – in Positron, File → Open Folder… – and the working directory is already right, so plain relative paths just work.

There is one more wrinkle worth knowing. Windows paths use backslashes (C:\Users\...), but a backslash means something special inside R strings. Use forward slashes even on Windows: "C:/Users/...". R handles the translation.

7.3 Say Where It Came From

Every project gets a README.md: a plain text file at the top of the folder saying what this is and where the data came from. It does not need to be long.

# Canola nitrogen trial, 2025

Question: how much does yield respond to nitrogen rate, and how much of
that association is really rainfall?

Data
  data/canola_trial.csv
    120 fields. Downloaded from [source] on 2026-08-18.
    Columns: field_id, fertilizer_kg_ha, rainfall_mm, variety, yield_bu_acre

Scripts
  R/01_clean.R      reads the raw file, fixes units, writes data/clean.csv
  R/02_analysis.R   correlation, regression, figures

The line that matters most is where the data came from and when you got it. A file called yields_final.csv with no provenance is close to useless a year later: you cannot tell whether it is the 2024 or 2025 release, whether you already cleaned it, or whether the numbers were revised after you downloaded them. Statistics Canada in particular revises past figures, so “downloaded 2026-08-18” is doing real work.

7.4 A Note on File Names

Two rules save a surprising amount of trouble.

No spaces or special characters. yield data (final).csv will work until the day it does not. Use yield_data_final.csv.

Dates as YYYY-MM-DD. 2025-09-15_deliveries.csv sorts chronologically on its own. Sept15.csv does not, and is ambiguous in half the world.

And a habit rather than a rule: if you find yourself writing final, final_v2, final_REAL in file names, that is a signal the project needs a way of tracking versions rather than a longer file name. There are tools for this – version control systems, of which Git is the common one – and you will meet them if you carry on with this kind of work.

7.5 Test Bank Sample

  1. (Structure.) A classmate sends you a folder containing one script and no data. What are they likely to have done wrong?
  2. (Paths.) Explain the difference between an absolute and a relative path, and say which belongs in a shared script.
  3. (setwd.) Why does a script containing setwd("C:/Users/peter/project") fail for everyone except Peter?
  4. (Raw data.) You spot three obviously wrong values in the CSV you were sent. Why should you not fix them in Excel and save?
  5. (README.) Name two things a README should record about a dataset, and say why each matters a year later.

7.6 Practice Exercises

  1. Set up a project folder for the canola trial with the layout above. Open it in Positron and confirm getwd() points where you expect.
  2. Write a script that reads data/canola_trial.csv using a relative path and writes a summary table to output/.
  3. Delete everything in output/ and re-run the script. Does it all come back? If not, why not?
  4. Write a README for the project, including where the data came from and what each script does.
