9  Cleaning Data

A file that opens without an error may still contain duplicate rows, inconsistent names, mixed units and missing values recorded as ordinary text. Cleaning starts by finding these problems. The decisions that follow depend on what the values mean and where the file came from.

The examples use grain_deliveries_messy.csv, a synthetic file constructed for this chapter to contain the problems discussed below. Read it without letting read_csv() trim spaces so that we can see the spaces in some crop names:

suppressPackageStartupMessages({
  library(tidyverse)
  library(janitor)
})

# Read the file and identify common missing-value codes
deliveries <- read_csv(
  "practice/data/grain_deliveries_messy.csv",
  na = c("", "NA", "N/A", "-", "."),
  trim_ws = FALSE
)

9.1 Tidy Data

The tidyverse is organized around tidy data (Wickham et al. 2023). A dataset is tidy when:

  1. Every variable has its own column.
  2. Every observation has its own row.
  3. Every value has its own cell.

Suppose a table records yield for three crops in two regions. In a tidy version the columns are region, crop and yield, and each row is one region-crop combination. In a wide version the columns are region, Canola, Wheat and Barley. The crop names are values of the variable crop, but they have been stored as column names.

The wide table may be easier to read. The long, tidy table is usually easier to analyze because crop is a column that can be filtered, grouped and plotted. This is the wide-versus-long distinction from Section 2.4.

Recognizing untidy data

Common signs include:

  • Values stored in column names. Columns named 2024, 2025 and 2026 usually contain values of a variable called year.
  • Several variables stored in one column. A value such as "South_InVigor" combines a region and a variety.
  • One observation spread over several rows. Price in one row and quantity in another row for the same market and year prevents either row from describing the observation on its own.

When you open a table, write down what one row represents and what each column represents. This usually makes the shape problem visible.

9.2 Tidying and Cleaning in Excel

Excel offers three approaches. Formulas can clean a file once while leaving the raw columns visible. Power Query can reshape the table and records each cleaning step. Find & Replace changes cells directly and leaves little evidence of what was changed.

9.2.1 Reshaping with Power Query

The RM yields file (Section 7.5.3) is wide, with one column for each crop. Power Query calls the wide-to-long operation Unpivot. Import the CSV with Data > Get Data > From Text/CSV, choose Transform Data, select Year and RM, and then choose Transform > Unpivot Columns > Unpivot Other Columns. Rename the two new columns crop and yield_bu_ac before loading the result.

Power Query returns 15,478 rows because Unpivot Other Columns drops source cells containing null. The R example below keeps those cells as NA and therefore returns 17,700 rows; add values_drop_na = TRUE to pivot_longer() when you want the two results to agree. The reverse operation is Pivot Column in Power Query or a PivotTable on a worksheet.

Cleaning with formulas

The workbook below keeps the raw delivery data in columns A through F and places cleaning formulas beside it. The formulas standardize crop names, rescale moisture values entered as decimals, count repeated ticket numbers and flag impossible weights. FORMULATEXT cells show the formulas, and summary checks appear below the table.

Download this workbook · Open online (File → Save a Copy to view formulas and edit)

The filter dropdown is useful when checking categories because it lists each distinct value. MIN, MAX, COUNTBLANK and a count of repeated identifiers cover many numerical checks. Excel’s summary functions silently ignore text in a numeric range, so add a separate text check such as =SUMPRODUCT(--ISTEXT(D5:D23)); a weight written as 38.2 t otherwise disappears from the summary without an error. Keep the raw columns beside the cleaned ones so that a changed value can be traced back.

Cleaning with Power Query

Power Query has recorded steps for the same work:

  • Remove Top Rows and Use First Row as Headers deal with files that begin with a title or notes.
  • The type icon in a column header sets a column to Text, Whole Number, Decimal or Date. A value that cannot be converted becomes an error that can be inspected.
  • Transform > Format > Trim removes extra spaces, and Capitalize Each Word standardizes capitalization.
  • Replace Values handles synonyms and missing-value codes. Power Query stores a missing value as null.
  • Remove Duplicates drops exact duplicates. To find a repeated identifier with different values, use Group By to count rows for each identifier and filter to counts above one.
  • Split Column > By Delimiter separates values that were stored together.
  • Fill > Down copies a category into blank cells below it when a spreadsheet records the label only once for a group of rows.

For dates, set delivery_date to Date and inspect conversion errors. If the whole source uses another convention, choose Change Type > Using Locale and state that convention. Opening the CSV directly lets Excel guess each cell: an ambiguous value such as 03/11/2025 can become the wrong date without an error. Power Query Editor requires a current desktop version of Excel 365 and is not available in Excel for the web.

Each operation appears in the Applied Steps list. Clicking a step shows the table at that point. When a new version of the source file arrives, Refresh runs the steps again.

  "practice/data/rm_yields_2015_2024.csv",
  show_col_types = FALSE

  pivot_longer(

9.3.2 Awkward Column Names

Column names such as Yield (bu/ac), REGION_NAME and Field ID Number are cumbersome in code. This book uses snake case: lower-case words separated by underscores, such as yield_bu_ac, region_name and field_id.

Use rename() when only a few names need changing. The new name goes on the left and the old name on the right:

# Make a small table with awkward names
awkward_names <- tibble(
  `Weight (t)` = c(42.1, 37.8),
  CROP_NAME = c("Canola", "Wheat")
)

awkward_names |>
  rename(
    weight_tonnes = `Weight (t)`,
    crop = CROP_NAME
  )
> # Make a small table with awkward names
> awkward_names <- tibble(
+   `Weight (t)` = c(42.1, 37.8),
+   CROP_NAME = c("Canola", "Wheat")
+ )
> 
> awkward_names |>
+   rename(
+     weight_tonnes = `Weight (t)`,
+     crop = CROP_NAME
+   )
# A tibble: 2 × 2
  weight_tonnes crop  
          <dbl> <chr> 
1          42.1 Canola
2          37.8 Wheat

janitor::clean_names() converts every name in a data frame to snake case. The package is installed once with install.packages("janitor"), then loaded in each new R session with library(janitor).

# Clean every column name in one call

  names()

9.3.3 Text in a Numeric Column

The first glimpse() reported weight_tonnes as <chr>, or character text. One row contains "38.2 t", so read_csv() could not treat the whole column as numeric. Find the values containing something other than a number, decimal point or minus sign:

# Find weights containing a unit or other text
deliveries |>
  filter(str_detect(weight_tonnes, "[^0-9.-]")) |>
  select(ticket_id, weight_tonnes)

9.3.5 Impossible Values

Every numeric variable has a possible range. A delivery weight cannot be negative and a moisture percentage cannot be 250. summary() is a quick way to inspect the minimum and maximum:

# Inspect the ranges of the numeric measurements
deliveries |>
  select(weight_tonnes, moisture_pct) |>
  summary()

# Display values outside their possible ranges
deliveries |>
  filter(weight_tonnes <= 0 | moisture_pct > 100) |>
  select(ticket_id, weight_tonnes, moisture_pct)
> # Inspect the ranges of the numeric measurements
> deliveries |>
+   select(weight_tonnes, moisture_pct) |>
+   summary()

 1st Qu.: 32.90   1st Qu.:  8.150

                  NAs    :2

> # Display values outside their possible ranges
> deliveries |>
+   filter(weight_tonnes <= 0 | moisture_pct > 100) |>

A negative weight may be a sign error or a reversed transaction. A moisture value of 250 may have lost its decimal point. Those are possible explanations, not facts. Correct a value only when the source supports the correction.

Here the synthetic file provides no defensible replacement values. Record that decision by treating the three impossible measurements as missing rather than silently carrying them into later summaries:

# Mark values outside the possible range as missing.
# This records a decision; it does not invent a correction.
deliveries <- deliveries |>
  mutate(
    weight_tonnes = if_else(
      weight_tonnes <= 0,
      NA,
      weight_tonnes
    ),
    moisture_pct = if_else(
      moisture_pct > 100,
      NA,
      moisture_pct
    )
  )
> # Mark values outside the possible range as missing.
> # This records a decision; it does not invent a correction.
> deliveries <- deliveries |>
+   mutate(
+     weight_tonnes = if_else(
+       weight_tonnes <= 0,
+       NA,
+       weight_tonnes
+     ),
+     moisture_pct = if_else(
+       moisture_pct > 100,

An extreme value can still be valid. A canola yield of 95 bu/ac is unusual, but it may belong to a very good field. Check it against the source and, if uncertainty remains, compare the analysis with and without it.

# Reconcile known synonyms while leaving other values unchanged
deliveries <- deliveries |>
  mutate(crop = case_when(
    crop == "Canola/Rapeseed" ~ "Canola",
    crop == "Soybean" ~ "Soybeans",

9.3.7 Mixed Units

Most moisture readings in the file are percentages near 8 to 15. Three values are below 1, which is not a plausible moisture percentage here; the intended construction of this teaching file confirms that they are proportions such as 0.099 rather than 9.9. The values are numeric, so they produce no parsing error.

# Find moisture readings recorded as decimal proportions
sum(deliveries$moisture_pct < 1, na.rm = TRUE)

deliveries |>
  filter(moisture_pct < 1) |>
  select(ticket_id, moisture_pct)

# Convert decimal proportions to percentages
deliveries <- deliveries |>
  mutate(
    moisture_pct = if_else(
      moisture_pct < 1,
      moisture_pct * 100,
      moisture_pct
    )
  )
> # Find moisture readings recorded as decimal proportions

> deliveries |>

9.3.8 Missing Values

R represents a missing value as NA. Most calculations involving NA return NA. The canola trial data has three fields with no rainfall reading:

# Read a file containing three missing rainfall values
trial_data <- read_csv(
  "practice/data/canola_trial.csv",
  show_col_types = FALSE
)

mean(trial_data$rainfall_mm)
mean(trial_data$rainfall_mm, na.rm = TRUE)
> # Read a file containing three missing rainfall values
> trial_data <- read_csv(
+   "practice/data/canola_trial.csv",
+   show_col_types = FALSE
+ )
> 
> mean(trial_data$rainfall_mm)
[1] NA
> mean(trial_data$rainfall_mm, na.rm = TRUE)
[1] 229.1017

The first call returns NA because three rainfall values are unknown. The second calculates the mean from the observed values. The argument na.rm = TRUE makes that decision visible. Many Excel functions skip blank cells automatically, so the missing values need to be counted separately there.

Missing values in disguise

A blank cell, "NA", "N/A", "-", "." and -999 may all mean that no value was recorded. The na argument in the first read_csv() call told R which text codes to treat as missing.

Count missing values in every column before deciding what to do with them:

# Count missing values in each column
deliveries |>
  summarise(
    across(everything(), \(x) sum(is.na(x)))
  )
> # Count missing values in each column
> deliveries |>
+   summarise(
+     across(everything(), \(x) sum(is.na(x)))
+   )
# A tibble: 1 × 6
  ticket_id delivery_date  crop weight_tonnes moisture_pct grade
      <int>         <int> <int>         <int>        <int> <int>
1         0             0     0             2            3     1

A numeric code such as -999 is more dangerous. R reads it as a number and includes it in calculations. summary() exposes it as an implausible minimum unless it is converted to NA when the file is read.

Working with missing values

is.na() identifies missing values and drop_na() removes rows that contain them:

# Count missing weights
sum(is.na(deliveries$weight_tonnes))

# Count rows retained after dropping any missing value
deliveries |>
  drop_na() |>
  nrow()

# Count rows retained when only analysis variables matter
deliveries |>
  drop_na(weight_tonnes, moisture_pct) |>
  nrow()

# Calculate a mean from the observed moisture readings
mean(deliveries$moisture_pct, na.rm = TRUE)
> # Count missing weights
> sum(is.na(deliveries$weight_tonnes))
[1] 2
> 
> # Count rows retained after dropping any missing value
> deliveries |>
+   drop_na() |>
+   nrow()
[1] 55
> 
> # Count rows retained when only analysis variables matter
> deliveries |>
+   drop_na(weight_tonnes, moisture_pct) |>
+   nrow()
[1] 56
> 
> # Calculate a mean from the observed moisture readings
> mean(deliveries$moisture_pct, na.rm = TRUE)
[1] 9.606897

The impossible-value decision above created missing values: there are now two missing weights and three missing moisture readings. The mean excludes the flagged moisture value of 250 rather than allowing it to distort the result. Dropping every incomplete row can remove far more data than dropping rows missing the variables used in a particular calculation.

When is dropping safe?

The answer depends on whether the chance a value is missing depends on the value itself. If a rain gauge failed at arbitrary times, the observed days may still represent the season, although there are fewer of them. If low-yielding farms were less likely to report, the remaining records will overstate average yield. In the deliveries file, omitting the three missing moisture readings would be less concerning if records were left blank for administrative reasons than if unusually wet loads were more likely to go unrecorded. Record how many values were missing, which observations were excluded and why the exclusion seemed reasonable.

9.3.9 Dates Stored as Text

glimpse() reported delivery_date as <chr> because most rows use 2025-09-07 while two use day/month/year. Text dates sort alphabetically and cannot be used in date arithmetic.

Parse the expected format and inspect the rows that fail. lubridate::ymd() warns when a value does not follow year-month-day order:

deliveries_with_dates <- deliveries |>
  mutate(date_parsed = lubridate::ymd(delivery_date))

# Display dates written in a different format
deliveries_with_dates |>
  filter(is.na(date_parsed)) |>

Once the checks are complete, write a derived file rather than editing the raw input:

write_csv(
  deliveries,
  "data/processed/grain_deliveries_clean.csv"
)

The raw file remains unchanged, the script records every decision, and rerunning it regenerates the clean file—the same principle as Refresh in Power Query.

9.4 A Checklist

Use these checks on a new file:

  1. Use glimpse() to check the dimensions, column names and types.
  2. Write down what one row represents and whether the table is tidy.
  3. Use summary() to inspect the ranges of numeric variables.
  4. Use count() on categorical variables and look for spelling and spacing differences.
  5. Check for exact duplicates and repeated identifiers.
  6. Count NAs in every column and look for other missing-value codes.
  7. Check that units are consistent and dates were read as dates.
  8. Record every correction, exclusion and assumption in the script or Power Query steps.
