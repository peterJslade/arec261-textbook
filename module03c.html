9  Merging Data

The data you need to answer one question often arrive in several tables. For example, suppose we wanted to understand the relationship between RM yields and precipitation. The yield data would come in one table, and the precipitation data would likely come in another. To answer our question, we would need to merge or join these tables.

Throughout this section, we will work with three datasets:

  • rm_yields_2015_2024.csv, with one row per RM per year. It contains 2,950 rows for ten years and six crops. Yields are measured in bushels per acre.
  • station_precip.csv, with one row per weather station per year. It contains May to August precipitation for sixteen stations and a count of days with no reading.
  • rm_lookup.csv, with one row per RM. It contains the RM name, census division, 2021 population and the closest of the sixteen weather stations.

We will do two merges:

  1. Merge the RM yields with the RM lookup. This will give us a dataset containing the closest weather station for each yield observation.
  2. Merge the dataset from step 1 with the weather station data. This will give us the growing-season precipitation for each observation.

Learning Objectives

By the end of this chapter you should be able to:

  1. Identify the key that connects two tables.
  2. Distinguish one-to-one, many-to-one and many-to-many relationships.
  3. Merge tables in Excel with Power Query, including a merge that uses two key columns.
  4. Merge tables in R with left_join() and related functions.
  5. Check for unmatched rows and unexpected changes in the row count.

Keys

A key is a column, or set of columns, used to identify and match rows across datasets. When we merge, we say that we merge on the key. The key must be present in both datasets.

In the three tables above, the keys for the two merges are:

  1. RM yields to RM lookup: RM.
  2. The resulting dataset to weather-station data: weather station and year.

One-to-one, many-to-one and many-to-many

There are three types of merges:

  • One-to-one (1:1). Each key value appears once in both tables. Grades and attendance both have one row per student-class, so the merged table has the same number of rows as either input.
  • Many-to-one (n:1). Values in the key column may repeat in one dataset but are unique in the other. In this example, students take many classes, so each student appears multiple times in the table on the left. Each class has a single professor, however, so each class appears only once in the table on the right.
  • Many-to-many (n:n). Values in the key column repeat in both datasets. In the figure, students take multiple classes (the table on the left), and each class can have multiple teaching assistants (the table on the right).

Before joining, decide which relationship you expect. Then compare the row counts before and after.

Both of our merges will be many-to-one:

  1. The RM yields dataset contains many observations for the same RM, but the RM lookup contains only one row for each RM.
  2. The merged dataset from step 1 contains many observations with the same closest weather station and year, but the weather-station dataset contains only one observation for each station and year.

9.1 Merging in Excel

NoteVideo walkthrough of this section

In Chapter 2, we used XLOOKUP to bring values from one table into another (Section 2.2). That approach is useful for a quick lookup. Here, we will use Power Query because it records the merge as a repeatable series of steps and can match on several columns directly.

Begin by importing rm_yields_2015_2024.csv and rm_lookup.csv with Data > Get Data > From Text/CSV > Transform Data. In the Power Query editor:

  1. Load the RM yield data using Power Query, transforming the data to longer format as we did before.
  2. Choose Power Query, select import csv, and select the RM lookup table.
  3. Select transform data. You will now see two queries on your left hand side (Figure 9.2).
  4. Select the first query (rm_yields_2015_2024) and then click Home > Merge Queries.
  1. In the pop up menu (Figure 9.3) select rm_lookup as the right table to merge.
  2. Select the key to merge on in each table by clicking its column heading: RM in the yields table and RM_Number in the lookup table.
  3. Keep Left Outer as the join kind. This keeps every yield observation and adds information wherever the lookup contains a matching RM.
  4. Check the number of matching rows reported at the bottom of the dialog – here every one of the 15,478 yield observations finds a match – then choose OK.
  1. The merged data arrives packed into a single new column whose every entry reads [Table] (Figure 9.4). Expand it using the double-arrow icon in its header: tick the columns you want (the RM name, census division, population and closest weather station) and untick Use original column name as prefix so the columns keep their own names.

Now you should see the RM lookup data merged with the RM yield data. We can now repeat the same process to merge once again with the station data: import station_precip.csv the same way, so a third query appears (Figure 9.6). The only difference is that we are now going to merge on both the station name and the year (Figure 9.7). Select Weather_Station and then Ctrl-click Year in the top table, and Station then Ctrl-click Year in the bottom one – the small 1 and 2 beside the headings show the matching order.

After expanding the precipitation column and choosing Close & load, every yield observation carries its RM’s name, closest station, and that station’s growing-season precipitation for the right year.

Checking the merge

After each merge, compare the number of rows with the original yields table. A many-to-one left merge should retain the same number of rows. Filter the expanded columns for null to find observations that did not match, and check several rows against the source tables.

Power Query also offers Inner, Full Outer and Left Anti joins. These correspond to the R joins introduced below. A Left Anti join is particularly useful for listing rows that have no match before completing the merge.

9.2 Merging in R

In tidyverse we merge data with join functions. There are four different types of joins depending on which data we want to keep in the merged file. Suppose we have two datasets y and x:

  • left_join(x, y, by) keeps every row of x whether it has a match in y or not. But does not keep rows in y that don’t have a match.
  • inner_join(x, y, by) keeps only rows that matched in both tables.
  • full_join(x, y, by) keeps every row from both tables, regardless of whether there is a match.
  • anti_join(x, y, by) returns the rows of x that have no match in y. It is useful for finding failed matches before a join.

The by argument specifies the keys we merge on. It can be a single column name or a vector of names.

Read the three files, standardizing the lookup and station column names on the way in (Section 8.3.2.1):

left_join() takes two data frames and a by argument that identifies the key. If a key has different names in the two tables, write join_by(left_name == right_name); a column with the same name on both sides is written once.

First join: yields and the RM lookup

The RM column is called rm in the yields table and rm_number in the lookup. Join, then compare the row counts:

# Add the RM information and nearest station
with_station <- yields_long |>
  left_join(rms,
            by = join_by(rm == rm_number),
            relationship = "many-to-one")

# Row counts before and after
nrow(yields_long)
nrow(with_station)

A many-to-one left join keeps every yield row, so the matching counts are the check that the merge behaved. The relationship = "many-to-one" argument records what we expect and makes left_join() stop if the lookup ever holds more than one row for an RM.

In R, text keys are sensitive to both case and spaces: "canola", "Canola" and "Canola " are three different keys. These differences have to be reconciled before the join (Section 8.3.2.5).

Second join: add the rain

The second key has two parts. The station column is called weather_station on the left and station on the right; year has the same name in both tables.

# Add precipitation for the matching station and year
merged <- with_station |>
  left_join(rain,
            by = join_by(weather_station == station, year),
            relationship = "many-to-one")

9.3 What the Merge Gives You

The merged table has one row per RM, year and crop, with yield and precipitation beside one another:

# Display the columns used in the analysis
merged |>
  select(year, rm, rm_name, crop, yield_bu_ac,
         weather_station, precip_may_aug_mm)

# Annual mean canola yield and precipitation
merged |>
  filter(crop == "Canola") |>
  summarise(
    canola_bu_ac = mean(yield_bu_ac),
    rain_mm = mean(precip_may_aug_mm),
    max_days_missing = max(days_missing),
    .by = year
  )

# Describe association, not causation
merged |>
  filter(crop == "Canola") |>
  summarise(
    yield_rain_correlation = cor(yield_bu_ac, precip_may_aug_mm)
  )

Across RM-years, wetter observations tend to have higher canola yield, but the relationship is loose: the correlation is about 0.41. The annual table also resists a simple rainfall story. Both 2021 and 2024 have low average yields despite ordinary or above-average rainfall. These data cannot say why. Testing whether heat contributed would require temperature data; explaining the remaining differences would require other variables as well.

The annual means average rainfall over RM rows, so a station serving more RMs receives more weight than a station serving fewer RMs. The merge has further limits that should be recorded in the project’s README. The median RM is 62 km from its assigned station, one quarter are more than 85 km away, and the maximum is 161 km, so station rainfall is a coarse proxy for rainfall across an RM. Some station-years also have many missing daily observations—up to 25 days in this file—and their seasonal totals sum only the available days, which biases those totals downward.
