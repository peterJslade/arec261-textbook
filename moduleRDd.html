9  Cleaning Data

Assume a new file is broken until you have checked. It was typed by someone in a hurry and exported by software that had its own ideas about formatting. This chapter starts with the shape a table should have, then tours the defects that show up most often in the values, how to find them, and what to do about them, first in Excel and then in R.

The examples below use grain_deliveries_messy.csv, a small file of grain deliveries carrying every defect in this chapter.

library(tidyverse)

deliveries <- read_csv("data/grain_deliveries_messy.csv")
glimpse(deliveries)

Learning Objectives

By the end of this chapter you should be able to:

  1. Explain what tidy data means, and reshape a dataset between wide and long with pivot_longer and pivot_wider.
  2. Clean up awkward column names with rename() and janitor::clean_names().
  3. Find duplicates, impossible values, inconsistent categories and mixed units in a new file.
  4. Recognize the disguises missing values wear, and count them properly.
  5. Decide – and justify – when dropping missing values is safe.
  6. Spot dates that imported as text, and say why it matters.
  7. Reshape and clean a table in Excel with Power Query, and say why its recorded steps matter.

9.1 Tidy Data

Before the defects in individual values, the shape of the whole table. The tidyverse is built around an idea called tidy data (Wickham et al. 2023). A dataset is tidy when:

  1. Every variable has its own column.
  2. Every observation has its own row.
  3. Every value has its own cell.

For example, this dataset is tidy:

  region  crop   yield
  South   Canola    41
  South   Wheat     52
  South   Barley    64
  Central Canola    44
  Central Wheat     55
  Central Barley    68

An observation here is a region-crop combination; the variables are region, crop, and yield. Each variable has a column and each observation has a row.

Now compare this version of the same data:

  region  Canola Wheat Barley
  South       41    52     64
  Central     44    55     68

This table is easier for a person to read, but it is not tidy. Canola, Wheat, and Barley are not three different variables; they are three values of the variable crop. This is the wide-versus-long distinction from Section 2.4, where a PivotTable needed the long form. For analysis in R, the long form is usually the more convenient one, because crop is an ordinary variable that R can filter by, group by, and compare.

Recognizing untidy data

Some common warning signs:

  • Values stored in column names. A table with columns region, 2024, 2025, 2026, where the year columns hold yields. The years are values of a variable called year; the tidy version has columns region, year, yield.
  • More than one variable in a column. A region_variety column containing "South_InVigor". That is two variables, region and variety, in one column.
  • One observation spread over several rows. Price in one row and quantity in another row for the same market and year.

What counts as an observation depends on the dataset and the question, but the basic test is always the same: what does one row represent? You should be able to answer that. When you first open a dataset, ask what one row represents, what each column represents, whether any values are hiding in column names, and whether any column holds several variables at once.

9.2 Tidying and Cleaning in Excel

Excel has two ways to clean a table: formulas beside the data, and Power Query. Formulas are quicker for a file you will clean once. Power Query is the one to learn, because it does the reshaping too, and it records what it did.

9.2.1 Reshaping with Power Query

The RM yields file (Section 7.3.5) is wide, one column per crop, and Power Query’s Unpivot turns it long. Import the file with Data > Get Data > From Text/CSV and press Transform Data to open the editor. Select the columns that identify a row, Year and RM, and choose Transform > Unpivot Columns > Unpivot Other Columns. Every crop column collapses into two: Attribute, holding the crop name that was in the header, and Value, holding the yield. Double-click the headers to rename them crop and yield_bu_ac, then Close & Load. 2,950 rows become 17,700, one per RM-year-crop.

The other direction, long to wide, is a PivotTable (Section 2.4), or Transform > Pivot Column in the same editor.

Cleaning with formulas

The workbook below holds the grain delivery tickets with the cleaning done in formula columns beside the raw data, so the original is still there to check against.

  • Categories. The filter dropdown on a column lists every distinct value in it, which is Excel’s count(). Open it on crop and the three spellings of canola are all visible at once. =PROPER(TRIM(C5)) fixes case and stray spaces; Find & Replace handles synonyms like Canola/Rapeseed.
  • Impossible values and mixed units. MIN and MAX at the foot of a column do what summary() does. An IF that rescales moisture readings under 1 is the if_else() from
  • Duplicates. Data > Remove Duplicates drops exact duplicates, and says how many it removed. It does nothing about the same ticket number with two different weights; =COUNTIF($A$5:$A$23, A5) beside each row finds those.
  • Text that should be numbers. A number stored as text shows a green triangle in the corner of the cell and sorts in the wrong place. VALUE() converts it, and Text to Columns (Section 7.2.1) converts a whole column at once if you click through with the type set to General.
  • Missing values. COUNTBLANK counts empty cells. Excel’s AVERAGE skips blanks without telling you, which is the difference from R’s NA (Section 9.3.7), so count them before you trust an average.

Cleaning with Power Query

Each of those has a Power Query equivalent, applied as a step in the editor rather than a formula in a cell. With the deliveries file open in the editor:

  • Remove Top Rows (Home > Remove Rows) drops a title and notes above the header, and Use First Row as Headers then promotes the real header.
  • Change Type, by clicking the icon in a column header, sets a column to Text, Whole Number, Decimal or Date. Rows that fail to convert show Error, which is how you find a 38.2 t in a numeric column.
  • Transform > Format > Trim and Capitalize Each Word fix spacing and case in crop.
  • Replace Values handles synonyms and disguised missing values: replace Canola/Rapeseed with Canola, or N/A with nothing, which Power Query stores as null, its NA.
  • Remove Duplicates (Home > Remove Rows) drops exact duplicates. Conflicting duplicates still need a count: Group By ticket_id with a row count, then filter to counts above 1.
  • Split Column > By Delimiter is Text to Columns inside the editor.
  • Fill > Down fills blanks from the cell above, for spreadsheets where a category was typed once and left blank for the rows beneath it.

The difference from formulas and from Find & Replace is that every step lands in the Applied Steps list on the right of the editor. You can click any step to see the table as it was at that point, delete one, or change its settings. When a new version of the file arrives, Refresh runs the whole list again. Formulas beside the data leave the original visible; a retyped cell or a Find & Replace on the sheet leaves nothing, and a month later there is no way to tell what was changed.

9.3 Tidying and Cleaning in R

9.3.1 Reshaping: pivot_longer and pivot_wider

Fixing the shape is the job of a pair of tidyr functions, which do what Unpivot and Pivot Column do in Power Query.

pivot_longer is Unpivot. You tell it which columns to gather, what to call the column that will hold their names, and what to call the column that will hold their values. The Saskatchewan RM yields again:

yields_wide <- read_csv("data/rm_yields_2015_2024.csv") |> clean_names()
yields_wide

yields_long <- yields_wide |>
  pivot_longer(cols = spring_wheat:peas,
               names_to = "crop",
               values_to = "yield_bu_ac")
yields_long

9.3.2 Awkward Column Names

The first thing to fix is often the names. Real files arrive with columns like Yield (bu/ac), REGION_NAME, or Field ID Number – readable to a person, but annoying to type and easy to mistype in code. This book prefers snake_case: lowercase, words separated by underscores, short but descriptive – yield_bu_ac, region, field_id.

For individual columns, rename() does it:

deliveries <- deliveries |>
  rename(weight_tonnes = "Weight (t)",
         crop = CROP_NAME)

For wholesale renaming, janitor::clean_names() converts every column to snake_case in one call – lowercase, underscores, special characters stripped. (It comes from the janitor package, not the tidyverse. Install it once with install.packages("janitor").)

library(janitor)
deliveries <- read_csv("data/grain_deliveries_messy.csv") |> clean_names()

Run it on almost anything you read in.

9.3.3 Duplicates

There are two kinds, and the second is the harder one.

An exact duplicate is the same row entered twice:

deliveries |> filter(duplicated(deliveries))     # show them
deliveries |> distinct()                          # drop them

A conflicting duplicate is the same identifier with different values: ticket T0030 appearing twice with two different weights. distinct() leaves these alone, because the rows are not identical. Count to find them:

deliveries |>
  count(ticket_id) |>
  filter(n > 1)

No code fixes this one. Somebody entered the delivery twice, or corrected it and left both rows, and you have to find out which is right. If you cannot, say so in the write-up and explain what you did.

9.3.4 Impossible Values

Every variable has values it cannot take. A weight cannot be negative, a moisture percentage cannot be 250, and a delivery of exactly zero tonnes is possible but odd.

summary() catches most of this in one line, because impossible values turn up in the minimum and maximum:

summary(deliveries)

Then look at the offending rows:

deliveries |> filter(weight_tonnes <= 0 | moisture_pct > 100)

A negative weight is probably a sign error or a reversed transaction. A moisture of 250 is probably 25.0 with a lost decimal point. Both of those are guesses, so record them as guesses. Dropping the rows without saying anything is the thing to avoid.

An impossible value is easy to rule on. A merely implausible one – a canola yield of 95 bu/ac, twice the provincial average – is a judgement call: it might be an error, or the best field in the province. Do not delete a value just because it is extreme. Check it against the source if you can, and if you cannot, analyze the data with and without it and report whether it changes the answer.

9.3.5 Inconsistent Categories

The same thing spelled several ways is the most common defect I run into, and it is easy to miss because every individual value looks fine. Count the categories:

deliveries |> count(crop)
  crop            n
  "CANOLA"        2
  "Canola"        6
  "canola"        4
  "Spring Wheat"  2
  "Spring wheat"  8
  "spring wheat"  5
  ...

Three spellings of canola and three of spring wheat, which group_by(crop) reads as six different crops.

Fix the mechanical cases first:

deliveries <- deliveries |>
  mutate(crop = str_trim(crop),        # strip stray spaces
         crop = str_to_title(crop))    # "CANOLA" and "canola" -> "Canola"

str_to_title handles capitalisation. read_csv already strips surrounding spaces, so str_trim is belt-and-braces here, but other readers do not, and a space you cannot see is a match you cannot explain.

Genuine synonyms like "Canola" and "Canola/Rapeseed" are a judgement call, so put them in an explicit recode where a reader can see the decision:

deliveries <- deliveries |>
  mutate(crop = case_when(
    crop == "Canola/Rapeseed" ~ "Canola",
    crop == "Soybean"         ~ "Soybeans",
    TRUE                      ~ crop
  ))

9.3.6 Mixed Units

A right value in the wrong unit is harder to catch than a wrong value, because nothing looks broken. In the deliveries file most moisture readings are percentages around 9.5, but a few were entered as decimals: 0.094 rather than 9.4. No error, no warning, and the mean comes out too low.

Knowing what range the variable should occupy is what catches it:

deliveries |> filter(moisture_pct < 1)

Grain moisture is normally 8 to 16 percent, so anything under 1 is in the wrong unit. Convert rather than drop:

deliveries <- deliveries |>
  mutate(moisture_pct = if_else(moisture_pct < 1, moisture_pct * 100, moisture_pct))

A file that records its own units in a column lets you convert with a case_when – one condition per unit, as in the crop-name recode above – instead of inferring from magnitude.

9.3.7 Missing Values

In R, a missing value is NA, and most operations propagate it: any calculation involving NA returns NA. The canola trial data has three fields with no rainfall reading – a rain gauge fails, or a value never gets recorded – so:

mean(trial_data$rainfall_mm)

mean(trial_data$rainfall_mm, na.rm = TRUE)
> mean(trial_data$rainfall_mm)
[1] NA
> 
> mean(trial_data$rainfall_mm, na.rm = TRUE)
[1] 229.1017

The first call says: calculate the mean of these observations. Three of them are unknown, so R cannot calculate the mean, and it returns NA rather than silently discarding information. The second call, with na.rm = TRUE (“remove NAs”), says: calculate the mean using the observations that are not missing. That may be exactly what we want – but now the decision is visible in the code.

This is an important difference from Excel, where many functions skip blank cells automatically. Real files complicate it further in two ways: missing values arrive in disguise, and deciding what to do with them takes some thought.

Missing values in disguise

Missing data shows up in real files in several forms: an empty cell, the text "NA", "N/A", "-", ".", or -999. R recognises the blank and NA. The rest come in as ordinary text and turn their column into <chr>.

Tell read_csv what counts as missing:

deliveries <- read_csv("data/grain_deliveries_messy.csv",
                       na = c("", "NA", "N/A", "-", "."))

Then count what you have before deciding anything:

deliveries |> summarise(across(everything(), ~ sum(is.na(.))))

A numeric code like -999 is the dangerous one. It will not turn the column to text; it will just be included in the mean as a number, which is another reason to run summary() on arrival and look at the minimum.

Working with missing values

A few patterns:

# Check for missing values
is.na(deliveries$weight_tonnes)              # logical vector
sum(is.na(deliveries$weight_tonnes))          # count of NAs

# Remove rows with any missing values
deliveries_clean <- deliveries |> drop_na()

# Remove rows with missing values in specific columns
deliveries_clean <- deliveries |> drop_na(weight_tonnes)

# Compute a statistic ignoring NAs
mean(deliveries$weight_tonnes, na.rm = TRUE)

# Replace NAs with a value
deliveries |> mutate(weight_tonnes = replace_na(weight_tonnes, 0))

When is dropping safe?

It depends on why the values are missing. If data is missing completely at random (a sensor failed arbitrarily), dropping missing values gives you unbiased estimates, just with less data. If data is missing for a reason related to the value itself (only high-yielding fields were reported), dropping them can bias your results – you will systematically overestimate yields.

The honest answer to “what should I do with missing values” is almost always: think about why they are missing, and document what you decided to do. There is no universal fix.

9.3.8 Dates Stored as Text

A date column that imported as <chr> cannot be sorted chronologically or used in arithmetic. It happens when the file mixes formats (2025-09-15 in some rows, Sept 15, 2025 in others), and it is worth catching early because arrange() on a text date sorts alphabetically without complaint.

glimpse() shows the problem (<chr> where you expected <date>). If the format is consistent, tell the reader what it is with col_types (Section 7.3.2); if it is mixed, the rows that failed to parse are found the same way as any other type problem:

deliveries |>
  filter(is.na(as.Date(delivery_date))) |>
  select(ticket_id, delivery_date)

Fixing messy dates properly uses tools we have not covered (the lubridate package is the standard one); for this course, it is enough to notice the problem and state the format explicitly when you read the file.

9.4 A Checklist

Run through this on every new file:

  1. glimpse() – are the column types what you expect?
  2. summary() – are the minimums and maximums possible?
  3. count() each categorical column – are the categories consistent?
  4. Count rows, and check for duplicated identifiers.
  5. Count NAs per column, and ask whether the missingness is random.
  6. Check the range of each numeric column against what the unit should be.
