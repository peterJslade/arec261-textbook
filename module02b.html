5  Working with Data in R

With R installed and the basics in hand, this chapter is about working with real data: setting up a project folder, installing the tidyverse, reading a CSV file, computing summary statistics, and getting a dataset into a shape you can analyze.

Learning Objectives

By the end of this chapter you should be able to:

  1. Set up a self-contained project folder that someone else can open and run.
  2. Install and load packages, and explain the difference between the two.
  3. Read a CSV file into R as a data frame, and diagnose file-not-found errors.
  4. Compute summary statistics in R, handling missing values correctly.
  5. Explain what “tidy data” means, and reshape a dataset with pivot_longer and pivot_wider.
  6. Clean up awkward column names.

5.1 One Folder Per Project

Before reading any data into R, set up a folder to work in. R always has a working directory – the folder it treats as “here” – and most of the file problems beginners hit come from R looking in a different place than they expect. The fix is a habit: keep each analysis in its own folder, and open that folder in Positron.

A layout that works for almost everything:

canola-trial/
  data/
    canola_trial.csv          <- exactly as it arrived
  R/
    01_clean.R
    02_analysis.R
  output/
    yield_by_variety.png
    summary_table.csv
  README.md

The project is self-contained. Everything the analysis needs is inside canola-trial/. You can zip the folder, send it to somebody, and it will run on their machine. A script that reaches out to a file elsewhere on your hard drive will not.

Raw data is never edited. data/ holds the file as it arrived. If you open the CSV in Excel, fix three cells and save, you have written over the only copy of what you were given, and there is no record of what you changed. Do the fixing in the script, where it leaves a trail.

Outputs are disposable. Anything in output/ can be deleted and regenerated by re-running the scripts. That is a useful test: delete output/, run the scripts, and see whether everything comes back.

Scripts are numbered in the order they run. 01_clean.R then 02_analysis.R. Six months later this tells you where to start.

To make the working directory be your project folder, open the folder in Positron with File → Open Folder…. Do this at the start of every session.

An organized project folder has one more payoff, which we will return to in Module 5: AI coding assistants can read the files in your project folder, so a well-organized project is one an assistant can actually help with.

5.2 Paths, and Why setwd() Is a Trap

A path tells R where a file is. There are two kinds.

An absolute path starts at the root of your hard drive:

read_csv("/Users/peter/Documents/canola-trial/data/canola_trial.csv")

A relative path starts wherever R currently is:

read_csv("data/canola_trial.csv")

The relative version works on any machine where the project folder is open. The absolute one works only on mine, because it names a user, a folder layout and an operating system that your classmate does not share.

R does have a function, setwd(), that changes the working directory from inside a script:

setwd("/Users/peter/Documents/canola-trial")     # do not do this

In my experience this is the most common reason a script that works fine for its author fails for everyone else. It writes one machine into a file you are going to share. Open the project folder instead, and plain relative paths work.

One wrinkle. Windows paths use backslashes, as in C:\Users\..., but a backslash means something special inside an R string. Write forward slashes even on Windows: "C:/Users/...". R handles the translation.

5.3 File Names

Two rules save a lot of trouble.

Avoid spaces and punctuation. yield data (final).csv will work until the day it does not. yield_data_final.csv is safer.

Write dates as YYYY-MM-DD. 2025-09-15_deliveries.csv sorts chronologically on its own, and Sept15.csv does not.

If you find yourself writing final, final_v2, final_REAL in file names, the project needs a way of tracking versions rather than a longer file name. Version control systems do this, and Git is the common one. It is worth learning if you carry on with this kind of work, though we will not cover it here.

5.4 Packages

A package is a bundle of extra functions someone has written that do not come with R itself. The one we will use constantly is the tidyverse, described in the next section. Using a package is a two-step process:

  1. Install it – once per computer. This downloads the package from the internet and saves it on your machine. You only ever do this once (per computer):

    install.packages("tidyverse")

    This prints a lot of text – progress bars and messages, sometimes in red. That red text is normal; it is not an error. Just wait for it to finish (it can take a few minutes the first time).

  2. Load it – once per script. Installing puts the package on your computer, but it is not switched on until you load it. Put this at the top of every script that uses the tidyverse:

    library(tidyverse)

If you skip the library() step and try to use a tidyverse function, R will stop with an error like:

Error in read_csv(...) : could not find function "read_csv"

That “could not find function” message almost always means you forgot to load the package (or you have not installed it yet). The fix is to run library(tidyverse) first. Note the quirk: you put quotes around the name when you install (install.packages("tidyverse")) but not when you load (library(tidyverse)).

5.5 The Tidyverse

The tidyverse is a collection of packages that share a common design: readr reads data, dplyr manipulates it, tidyr reshapes it, and ggplot2 graphs it, among others. Installing the tidyverse installs the whole collection, and library(tidyverse) loads the core packages at once. It has become the standard way of working with tabular data in R, and it is what this book uses.

Base R can do most of the same things, and you will sometimes see base functions in other people’s code or in AI-generated code. The two styles mix fine; we simply teach the tidyverse versions.

TipOther resources — packages and the tidyverse
  • R for Data Science (2nd ed.) – the Introduction describes the tidyverse workflow (import → tidy → transform → visualize → model → communicate) this course follows.
  • tidyverse.org – the package index lists the core packages and what each does.

5.6 Reading Data from CSV

The dataset for this chapter and the next is field_yields.csv – 60 canola fields with columns field_id, region, variety, acres, yield_bu_acre, year, seeding_date, and units. Download it and put it in your project’s data/ folder.

Once the tidyverse is loaded, you can read it:

yields <- read_csv("data/field_yields.csv")

read_csv reads the file into a data frame and saves it in the object yields. It also prints a short note about what column types it guessed – check them, because R guesses well but not perfectly.

The path "data/field_yields.csv" is relative: R starts from the working directory and looks for a data/ folder inside it. If you opened your project folder (Section 5.1), that is exactly where the file is, and this just works. If R cannot find the file, you get:

Error: 'data/field_yields.csv' does not exist in current working directory (...)

Two things to check, in order:

  • Did you open the project folder? File → Open Folder… in Positron, then pick the folder that contains data/.
  • Where does R think it is? Run getwd() (“get working directory”). It prints the folder R is currently using; the error message shows it too.

A couple more notes:

  • If your file uses semicolons or tabs instead of commas, use read_csv2 or read_tsv.
  • To save a data frame back out, write_csv(yields, "output/yields_clean.csv") is the mirror image of read_csv.

Once you have the data in, you can explore it:

yields              # prints the data frame (first 10 rows)
head(yields)        # first 6 rows
tail(yields)        # last 6 rows
nrow(yields)        # number of rows
ncol(yields)        # number of columns
names(yields)       # column names
glimpse(yields)     # compact column-by-column view, with types
summary(yields)     # quick summary of every column

summary() is especially useful as a first look at a new dataset. For every numeric column it reports the min, max, mean, median, and quartiles; for text columns it simply notes how many values there are. Always run it when you open a new dataset.

  • readr documentation – the tidyverse readr reference for read_csv() and its relatives.

5.7 Summary Statistics in R

All the summary statistics from Module 1 exist in R too. For the rest of the chapter the examples use field_yields.csv – 60 canola fields with columns field_id, region, variety, acres, yield_bu_acre, year, seeding_date, and units. Put it in your project’s data/ folder and read it in:

library(tidyverse)

yields <- read_csv("data/field_yields.csv")

Then:

mean(yields$yield_bu_acre)
median(yields$yield_bu_acre)
sd(yields$yield_bu_acre)
var(yields$yield_bu_acre)
min(yields$yield_bu_acre)
max(yields$yield_bu_acre)
range(yields$yield_bu_acre)              # returns c(min, max)
quantile(yields$yield_bu_acre, 0.25)
quantile(yields$yield_bu_acre, c(0.25, 0.5, 0.75))  # multiple at once
IQR(yields$yield_bu_acre)

One thing to watch for: if your data has missing values (coded as NA in R), these functions will return NA by default. To compute the statistic ignoring the missing values, pass na.rm = TRUE:

mean(yields$yield_bu_acre)

mean(yields$yield_bu_acre, na.rm = TRUE)
> mean(yields$yield_bu_acre)
[1] NA
> 
> mean(yields$yield_bu_acre, na.rm = TRUE)
[1] 45.86316

If mean() returns NA unexpectedly, the first thing to check is whether your data has missing values. This default is deliberate – silently ignoring missing values (as Excel often does) hides a problem you should know about. We return to missing values properly when we clean data in Module 3.

TipOther resources — summary statistics in R
  • Video – Rob Spencer, Descriptive statistics using the summary function – a short walkthrough of summary().
  • Video – Dr E Research Videos, Basic summary statistics in R – mean, median, standard deviation, and the number summary.

5.8 Tidy Data

Hadley Wickham (one of the creators of the tidyverse) has written extensively about what he calls tidy data (Wickham et al. 2023). The idea is simple: a dataset is “tidy” if:

  1. Every variable has its own column.
  2. Every observation has its own row.
  3. Every value has its own cell.

That sounds obvious, but a huge fraction of real datasets violate it. Common problems:

  • Column headers are values, not variable names. For example, a table with columns 2020, 2021, 2022, 2023 where each column contains yields. The column header should be a variable called year; the values should be in a single yield column.
  • Multiple variables in one column. For example, a region_variety column that contains "South_InVigor". These should be two separate columns.
  • Observations split across rows. For example, one row for price and another for quantity of the same product. These should be columns.

You can do analysis on untidy data, but it is much harder. Almost every tool in the tidyverse assumes tidy input. If your data is not tidy, your first step should usually be to make it tidy.

Reshaping with pivot_longer and pivot_wider

This is the wide-versus-long distinction from Section 2.4, where a PivotTable needed the long form. The same data can be stored wide – one column per crop – or long, with the crop as a variable:

yields_wide <- tibble(
  region = c("South", "Central", "North"),
  Canola = c(41, 44, 38),
  Wheat  = c(52, 55, 49),
  Barley = c(64, 68, 60)
)
yields_wide
> yields_wide <- tibble(
+   region = c("South", "Central", "North"),
+   Canola = c(41, 44, 38),
+   Wheat  = c(52, 55, 49),
+   Barley = c(64, 68, 60)
+ )
> yields_wide
# A tibble: 3 × 4
  region  Canola Wheat Barley
  <chr>    <dbl> <dbl>  <dbl>
1 South       41    52     64
2 Central     44    55     68
3 North       38    49     60

The wide table is untidy in the first way listed above: the column headers Canola, Wheat, Barley are values of a variable (crop), not variables themselves. pivot_longer fixes it. You tell it which columns to gather, what to call the column that will hold their names, and what to call the column that will hold their values:

yields_long <- pivot_longer(yields_wide,
                            cols = c(Canola, Wheat, Barley),
                            names_to = "crop",
                            values_to = "yield")
yields_long
> yields_long <- pivot_longer(yields_wide,
+                             cols = c(Canola, Wheat, Barley),
+                             names_to = "crop",
+                             values_to = "yield")
> yields_long
# A tibble: 9 × 3
  region  crop   yield
  <chr>   <chr>  <dbl>
1 South   Canola    41
2 South   Wheat     52
3 South   Barley    64
4 Central Canola    44
5 Central Wheat     55
6 Central Barley    68
7 North   Canola    38
8 North   Wheat     49
9 North   Barley    60

Nine rows now: one per region-crop combination, with crop and yield as ordinary columns that R can group and filter on.

pivot_wider goes the other way. Tell it which column holds the names and which holds the values:

pivot_wider(yields_long, names_from = crop, values_from = yield)
> pivot_wider(yields_long, names_from = crop, values_from = yield)
# A tibble: 3 × 4
  region  Canola Wheat Barley
  <chr>    <dbl> <dbl>  <dbl>
1 South       41    52     64
2 Central     44    55     68
3 North       38    49     60

Long is usually what analysis wants; wide is often what people want to read. Expect to pivot in both directions – data from Statistics Canada, for example, typically arrives long and needs widening for a report table.

For now the point is: when you are reading in a dataset, look at the shape. Is each row an observation? Is each column a variable? If not, fixing that is the first step.

  • R for Data Science (2nd ed.) – Chapter 5, “Data tidying” is the definitive treatment of tidy data, pivot_longer, and pivot_wider.
  • Video – Riffomonas Project, Reshaping data to be long or wide with pivot_longer and pivot_wider.

5.9 Renaming and Cleaning Column Names

Real-world datasets often have terrible column names: Yield (bu/ac), REGION_NAME, X1. These will work in R but are annoying to type and easy to mistype. Clean them up early:

yields <- rename(yields,
                 yield_bu_ac = "Yield (bu/ac)",
                 region = REGION_NAME)

For wholesale renaming, janitor::clean_names() is invaluable. (This is from the janitor package, not the tidyverse. Install it once with install.packages("janitor").)

library(janitor)
yields <- clean_names(read_csv("data/messy_data.csv"))

clean_names converts everything to lowercase with underscores, strips special characters, and generally makes your column names nice. I use it on almost every dataset I read in.

  6. (Errors.) read_csv("data/yields.csv") returns a “does not exist” error even though the file exists. Give two things to check.
  7. (Summary.) Write R code that computes the mean, median, and standard deviation of the yield_bu_acre column, ignoring any missing values.
  8. (Tidy data.) A table has columns region, 2023, 2024, 2025, where the year columns hold yields. Say why this is untidy and write the pivot_longer call that fixes it.
  9. (Reshaping.) When would you use pivot_wider? Give an example.
  10. (Names.) What does janitor::clean_names() do, and why is it useful?

5.11 Practice Exercises

Use the field_yields.csv dataset for these.

  1. Set up a project folder with data/, R/, and output/ subfolders. Put field_yields.csv in data/ and open the folder in Positron. Confirm getwd() points where you expect.
  2. Write a script that reads the data with a relative path and prints glimpse() and summary() of it.
  3. The dataset has a few fields with a missing (NA) yield. Compute the mean yield with and without na.rm = TRUE and explain the difference.
  4. Build the small wide table from Section 5.8 by hand with tibble(), pivot it longer, then pivot it back.
  5. Delete everything in output/, re-run your script, and check that everything comes back. If not, why not?
