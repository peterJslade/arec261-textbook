5  Working with Data in R

In the last chapter, we created small datasets directly in R. Real data analysis usually starts somewhere else: with a file. That creates a few practical questions. Where should the file go? How does R find it? How do we bring it into R? And once it is there, how do we check that R has read it correctly?

This chapter develops a simple workflow for working with real data: keep everything for an analysis in one project folder, refer to files with relative paths, use packages to add functions to R, read the data from a CSV file, inspect it before doing any analysis, and recognize whether it is organized in a useful shape. These habits are not exciting, but they prevent a remarkable number of problems later.

Learning Objectives

By the end of this chapter you should be able to:

  1. Set up a self-contained project folder for an analysis.
  2. Explain the difference between an absolute and a relative path.
  3. Install and load an R package, and explain the difference between the two.
  4. Read a CSV file into R as a data frame.
  5. Inspect a new dataset and identify common problems.
  6. Calculate basic summary statistics while handling missing values correctly.
  7. Explain what tidy data means and recognize data that needs to be reshaped.

5.1 One Folder Per Project

Before we read any data into R, we need somewhere to put it. A good rule: keep everything for one analysis inside one project folder. Suppose we are analyzing a canola variety trial. Our folder might look like this:

canola-trial/
  data/
    canola_trial.csv          <- exactly as it arrived
  R/
    01_clean.R
    02_analysis.R
  output/
    yield_by_variety.png
    summary_table.csv
  README.md

data/ contains the original data; R/ contains the scripts, numbered in the order they run; output/ contains tables, figures, and other results the scripts produce; and README.md holds notes explaining the project. The exact folder names matter less than the principle: the project is self-contained. If you zip canola-trial/ and send it to somebody else, they have everything they need to run your analysis. A script that reaches out to a file elsewhere on your hard drive will not travel like that.

Raw data is never edited. Suppose canola_trial.csv contains an obvious typo. You could open the file in Excel, fix the cell, and save – but then there is no record of what you changed, and you have written over the only copy of what you were given. Keep the original file exactly as it arrived and make the correction in your R script, where it leaves a trail: what changed, and how.

Outputs are disposable. The opposite principle applies to output/: everything there should be something your scripts can recreate. Deleting the contents of output/ and seeing whether your scripts regenerate everything is a useful test of whether an analysis is reproducible.

To make this work, open the project folder itself in Positron at the start of a session: File → Open Folder…, then choose the folder containing data/, R/, and output/. R now treats this folder as its starting point when it looks for files, which makes the paths in the next section much simpler.

NoteWhy this matters for AI

AI coding assistants also work better when the relevant scripts and files are organized together. When we use AI tools later in the book (Module 5), a well-organized project gives the assistant useful context about the analysis.

5.2 Paths, and Why setwd() Is a Trap

A path tells R where to find a file. There are two kinds.

An absolute path gives the file’s complete location on one computer:

read_csv("/Users/peter/Documents/canola-trial/data/canola_trial.csv")

A relative path describes the location relative to the project folder:

read_csv("data/canola_trial.csv")

The second version is much better. The absolute path contains information specific to one computer: the username peter, the location of the Documents folder, and the operating system’s folder layout. If I send that script to you, you probably do not have /Users/peter/Documents/. But if we both have the same project folder, we both have data/canola_trial.csv. So the rule is: open the project folder in Positron, and use relative paths inside your scripts.

R does have a function, setwd(), that changes the working directory from inside a script:

setwd("/Users/peter/Documents/canola-trial")     # do not do this

You will see this in old scripts and online examples. Do not put a line like it in a script you intend to share: it solves the path problem on your computer by creating a path problem on everybody else’s. This is the most common reason a script that works fine for its author fails for everyone else.

If you are ever unsure where R thinks it is, run getwd() (“get working directory”). R prints the folder it is currently treating as its starting point.

NoteWindows note

Windows displays paths with backslashes, as in C:\Users\Peter\Documents, but a backslash means something special inside an R string. Write forward slashes even on Windows: "C:/Users/Peter/Documents". R handles the translation.

TipFile names

Two rules save a lot of trouble. Use short descriptive names without spaces or punctuation: yield_data_final.csv, not Field Yields FINAL!!.csv. And write dates as YYYY-MM-DD: 2026-09-15_deliveries.csv sorts chronologically on its own, and Sept15.csv does not.

If you find yourself writing final, final_v2, final_REAL in file names, the project needs version control rather than longer file names. Git is the common system; we will not cover it here.

5.3 Packages

R comes with hundreds of useful functions. Other people have written thousands more and bundled them into packages – add-ons that give R additional functions. Using a package is a two-step process:

  1. Install it – once per computer. This downloads the package from the internet and saves it on your machine:

    install.packages("tidyverse")

    The first installation can take a few minutes and prints a lot of messages. Some appear in red even when nothing has gone wrong; what matters is whether R ultimately reports an error.

  2. Load it – once per script. Installing puts the package on your computer, but it is not switched on until you load it. Put this at the top of every script that uses the tidyverse:

    library(tidyverse)

If you skip the library() step and try to use a package function, R will stop with an error like:

Error in read_csv(...) : could not find function "read_csv"

That “could not find function” message almost always means you forgot to load the package (or you have not installed it yet). The fix is to run library(tidyverse) first. Note the quirk: you put quotes around the name when you install (install.packages("tidyverse")) but not when you load (library(tidyverse)). The reason is not important yet; just recognize the pattern.

5.4 The Tidyverse

The package we will use most is actually a collection of packages called the tidyverse. Different tidyverse packages do different jobs, and four will matter most in this book:

Package Main job
readr reading data
dplyr manipulating data
tidyr reshaping data
ggplot2 making graphs

Installing the tidyverse installs these and several others, and library(tidyverse) loads the core packages at once. The tidyverse has become the standard way of working with tabular data in R, and it is what this book uses: its packages share a consistent style and provide particularly convenient tools for tables of data.

Base R can do many of the same things, and you will see base functions in documentation, online examples, and AI-generated code. There is nothing wrong with mixing the two. In this chapter we use readr to bring data into R; in the next chapter we use dplyr to manipulate it.

TipOther resources — packages and the tidyverse
  • R for Data Science (2nd ed.) – the Introduction describes the tidyverse workflow (import → tidy → transform → visualize → model → communicate) this course follows.
  • tidyverse.org – the package index lists the core packages and what each does.

5.5 Reading Data from CSV

The dataset for this chapter and the next is field_yields.csv – 60 canola fields with columns field_id, region, variety, acres, yield_bu_acre, year, seeding_date, and units. Download it and put it in your project’s data/ folder, and make sure you have opened the project folder itself in Positron.

Start your script by loading the tidyverse, then read the file:

library(tidyverse)

yields <- read_csv("data/field_yields.csv")

Read the second line from right to left: read field_yields.csv from the data folder, and save the resulting data frame as yields. After running it, yields is an object in R.

read_csv also prints a short note about the column types it guessed – numeric, character, date, and so on. R guesses well but not perfectly, which is one reason we always inspect a dataset after reading it.

When R cannot find the file

A common error looks like this:

Error: 'data/field_yields.csv' does not exist in current working directory (...)

Do not start changing the code randomly. Check two things, in order:

  • Did you open the correct project folder? File → Open Folder… in Positron; the folder you open should contain data/.
  • Where does R think it is? Run getwd() and look at the folder it prints. Starting from that folder, can you go into a folder called data and find field_yields.csv? If yes, the path works.

A few related functions

CSV means comma-separated values, but text data can be separated in other ways. read_csv2 reads files that use semicolons; read_tsv reads tab-separated files. And write_csv is the mirror image of read_csv – one brings data into R, the other writes it out:

write_csv(yields, "output/yields_clean.csv")

Inspecting the data

Successfully reading a file does not mean you are ready to analyze it. Inspect it first:

yields              # prints the data frame (first 10 rows)
head(yields)        # first 6 rows
nrow(yields)        # number of rows
ncol(yields)        # number of columns
names(yields)       # column names
glimpse(yields)     # compact column-by-column view, with types
summary(yields)     # quick summary of every column

glimpse() shows each column and its type; summary() reports the min, max, mean, median, and quartiles of every numeric column. The goal is not to run these commands mechanically but to answer some questions:

  • Did I get the number of observations I expected?
  • Are the variables I expected actually present?
  • Did R interpret numeric variables as numbers?
  • Are the values in plausible ranges?
  • Are there missing values?

Looking at the data before analyzing it catches many mistakes cheaply.

Viewing Data in Positron

You can also inspect the data visually. After you run the read_csv line, yields appears in the Variables pane. Click it and Positron opens the Data Explorer: a spreadsheet-style view of the data.

The Data Explorer has two parts. The grid shows the rows and columns, and you can sort and filter them by clicking the column headers. The summary panel shows, for each column, its type, the percentage of missing values, and a small sketch of its distribution. Some problems are much easier to notice by looking at the data than by reading console output.

There is one important difference from Excel: the Data Explorer is for viewing data, not fixing it. You cannot change a cell. The file in data/ stays as it arrived, and any correction happens in the script, where it is recorded.

5.6 Summary Statistics in R

Once the data are in R, we can calculate the same summary statistics we used in Excel. yield_bu_acre is a column of the data frame yields, so we refer to it as yields$yield_bu_acre:

mean(yields$yield_bu_acre)
median(yields$yield_bu_acre)
sd(yields$yield_bu_acre)
var(yields$yield_bu_acre)
min(yields$yield_bu_acre)
max(yields$yield_bu_acre)
range(yields$yield_bu_acre)              # returns c(min, max)
quantile(yields$yield_bu_acre, 0.25)
quantile(yields$yield_bu_acre, c(0.25, 0.5, 0.75))  # multiple at once
IQR(yields$yield_bu_acre)

The statistical ideas have not changed since Module 1; only the way we ask the computer to calculate them has.

Missing values

Real datasets often contain missing observations, which R represents as NA. Some of our 60 fields are missing a yield, so this happens:

mean(yields$yield_bu_acre)

mean(yields$yield_bu_acre, na.rm = TRUE)
> mean(yields$yield_bu_acre)
[1] NA
> 
> mean(yields$yield_bu_acre, na.rm = TRUE)
[1] 45.86316

The first call says: calculate the mean of these observations. One of them is unknown, so R cannot calculate the mean, and it returns NA rather than silently discarding information. The second call, with na.rm = TRUE (“remove NAs”), says: calculate the mean using the observations that are not missing. That may be exactly what we want – but now the decision is visible in the code.

This is an important difference from Excel, where many functions skip blank cells automatically. Neither behavior solves the underlying statistical problem of missing data; for now, the point is that if R unexpectedly returns NA, check whether your data contains missing values. We return to missing data properly when we clean datasets in Chapter 9.

5.7 Tidy Data

Before analyzing a dataset, we also need to think about its shape. The tidyverse is built around an idea called tidy data (Wickham et al. 2023). A dataset is tidy when:

  1. Every variable has its own column.
  2. Every observation has its own row.
  3. Every value has its own cell.

For example, this dataset is tidy:

  region  crop   yield
  South   Canola    41
  South   Wheat     52
  South   Barley    64
  Central Canola    44
  Central Wheat     55
  Central Barley    68

An observation here is a region-crop combination; the variables are region, crop, and yield. Each variable has a column and each observation has a row.

Now compare this version of the same data:

  region  Canola Wheat Barley
  South       41    52     64
  Central     44    55     68

This table is easier for a person to read, but it is not tidy. Canola, Wheat, and Barley are not three different variables; they are three values of the variable crop. This is the wide-versus-long distinction from Section 2.4, where a PivotTable needed the long form. For analysis in R, the long form is usually the more convenient one, because crop is an ordinary variable that R can filter by, group by, and compare.

Recognizing untidy data

Some common warning signs:

  • Values stored in column names. A table with columns region, 2024, 2025, 2026, where the year columns hold yields. The years are values of a variable called year; the tidy version has columns region, year, yield.
  • More than one variable in a column. A region_variety column containing "South_InVigor". That is two variables, region and variety, in one column.
  • One observation spread over several rows. Price in one row and quantity in another row for the same market and year.

What counts as an observation depends on the dataset and the question, but the basic test is always the same: what does one row represent? You should be able to answer that. When you first open a dataset, ask what one row represents, what each column represents, whether any values are hiding in column names, and whether any column holds several variables at once.

Reshaping a dataset between the wide and long forms is done by a pair of functions, pivot_longer and pivot_wider, covered with the rest of the cleaning toolkit in Section 9.8. For now, the goal is to recognize the shape that analysis wants.

TipOther resources — tidy data
  • R for Data Science (2nd ed.) – Chapter 5, “Data tidying” develops the tidy-data idea and shows how datasets are reshaped between long and wide forms.
  • Video – Riffomonas Project, Reshaping data to be long or wide with pivot_longer and pivot_wider.

5.8 Column Names

Column names matter because we type them repeatedly. Real datasets sometimes arrive with names like Yield (bu/ac), REGION_NAME, or Field ID Number – readable to a person, but awkward in code. This book prefers names like yield_bu_ac, region, and field_id: lowercase, words separated by underscores, short but descriptive. This style is called snake_case.

You do not need to fix every imperfect name immediately. But when you inspect a new dataset with names(), look for names that will make the analysis unnecessarily awkward. The next chapter shows how to rename columns in code, and Chapter 9 covers cleaning up a whole set of bad names at once.

5.9 Putting the Workflow Together

The whole chapter fits in one short script. Suppose the project contains:

field-yields/
  data/
    field_yields.csv
  R/
    01_explore.R
  output/

Open field-yields/ in Positron and create R/01_explore.R:

# ---
# Title: Explore field yield data
# Author: Your Name
# Date: 2026-09-29
# ---

# Load packages
library(tidyverse)

# Read data
yields <- read_csv("data/field_yields.csv")

# Inspect structure
nrow(yields)
names(yields)
glimpse(yields)

# Inspect values
summary(yields)

# Summarize yield
mean(yields$yield_bu_acre, na.rm = TRUE)
median(yields$yield_bu_acre, na.rm = TRUE)
sd(yields$yield_bu_acre, na.rm = TRUE)

Notice what the script does not contain: no setwd(), no reliance on manually edited data, and no jump straight from reading the file to analysis without checking what came in. It follows the workflow this chapter has been building: open the project, load packages, read the data, inspect it, check for problems, and only then analyze.
